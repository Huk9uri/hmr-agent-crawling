## 1. 변경 목적

채널별 주문 API가 허용하는 최대 조회기간을 다시 확인하고, 매일 실행되는 주문 수집에서 주문 생성 이후 변경되는 상태(결제, 출고, 배송, 취소 등)를 놓치지 않도록 조회 구간을 조정했다.

이번 변경은 최초 실행만 과거 데이터를 적재하고 이후에는 전일 주문만 가져오는 방식이 아니다. 일일 배치는 채널별 허용 범위만큼 최근 주문을 매번 다시 조회하며, DB에서는 기존 최신 데이터와 비교하여 신규·변경·동일 데이터를 구분한다.

|---|---:|---:|---|
| 고도몰 | 1일 | 31일 | 실행 기준일 포함 최근 31일 |
| 11번가 | 1일 | 31일 | 실행 기준일 포함 최근 31일 |

고도몰과 11번가 모두 인증된 읽기 전용 API 호출로 31일 구간 조회가 정상 처리되는 것을 확인한 뒤 최대 조회기간을 31일로 변경했다. 따라서 매일 최근 31일의 주문 상품 정보를 다시 확인하고, 주문 후 뒤늦게 변경된 상태도 적재 대상에 포함한다.

운영 반영 전 확인 결과는 다음과 같다.

- 고도몰 31일 조회: 성공, 3페이지, 195건 응답
- 11번가 31일 조회: 성공, 2페이지, 조회 시점 응답 0건

11번가의 0건은 API 호출 실패가 아니라 해당 테스트 기간에 조회된 주문이 없었다는 의미다.

## 3. 네이버 조회 방식과 의도적 중복

네이버 변경상품주문 조회 API는 한 요청의 조회 범위를 24시간 이내로 제한한다. 배치 실행 시각인 14:00 KST까지 안정적으로 포함하기 위해 하루 수집을 다음 두 요청으로 나누었다.

예를 들어 2026-09-02 14:00 배치는 다음과 같이 호출한다.

1. `2026-09-01 13:50:00 ~ 2026-09-02 13:40:00` — 23시간 50분
2. `2026-09-02 13:40:00 ~ 2026-09-02 14:00:00` — 20분

두 요청은 `13:40` 경계를 공유한다. 또한 다음 날인 2026-09-03의 첫 요청은 `2026-09-02 13:50`부터 시작하므로, 전날 두 번째 요청의 `13:50~14:00` 구간을 10분간 다시 조회한다.

이 10분 중첩은 오류가 아니라 다음 상황에서 경계 데이터가 누락될 가능성을 줄이기 위한 의도적 안전 구간이다.

- API 응답 반영 지연
- 배치 실행 시각의 미세한 차이
- 조회 시작·종료 경계의 포함 여부 차이

네이버는 주문 생성일 전체를 최근 31일 동안 반복 조회하는 방식이 아니라, `lastChanged` 기준 최근 약 24시간의 변경상품주문을 위 구간으로 조회한다. 따라서 과거에 생성된 주문이라도 해당 기간에 상태가 변경되면 다시 수집된다.

## 4. 중복 적재 방지

조회 구간을 반복하거나 겹치게 호출해도 같은 데이터가 무조건 새 행으로 쌓이지 않도록 다음 단계에서 중복을 처리한다.

1. 네이버 API 수집 단계에서 두 요청과 페이지 전체의 `ProductOrderId`를 합치고 중복 ID를 제거한다.
2. 상세 주문 조회는 중복 제거된 상품주문번호를 기준으로 수행한다.
3. DB 저장 단계에서 채널별 주문상품 식별키로 현재 최신 행을 찾고 payload hash를 비교한다.
4. 내용이 같으면 `skipped`, 내용이 변경되면 기존 최신 행을 해제하고 변경 이력으로 신규 행을 적재하며, 처음 확인된 주문이면 신규 적재한다.

따라서 31일 반복 조회와 네이버의 10분 중첩은 누락 방지를 위한 조회 전략이며, 동일 내용의 중복 이력을 생성하기 위한 동작이 아니다.
