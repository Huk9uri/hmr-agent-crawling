# 채널별 주문·배송 API 전체 필드 적재 설계

- 작성일: 2026-08-11
- 대상 DBMS: Microsoft SQL Server
- 대상 프로젝트: `HMR_Agent_Crawling`

## 1. 목적

각 판매채널의 주문·배송 Open API가 제공하는 업무 정보를 채널별 테이블에 최대한 명시적인 컬럼으로 저장한다. 채널 간 공통 지표의 제공 여부는 이번 적재 범위를 제한하지 않는다. 이후 대시보드 또는 분석 담당자가 채널별 테이블이나 별도 VIEW에서 필요한 컬럼을 선택해 사용한다.

현재 구현된 일곱 개 채널을 우선 대상으로 한다.

1. 네이버 스마트스토어
2. 토스쇼핑
3. 한촌몰·고도몰
4. 쿠팡 WING
5. 롯데ON
6. SSG.COM
7. 11번가

CJ온스타일, 네이버페이, G마켓, 옥션, 알리익스프레스는 인증·권한을 확보하고 실제 응답을 확인한 뒤 동일한 규칙으로 별도 테이블을 추가한다.

## 2. 핵심 설계 원칙

### 2.1 채널 고유 스키마

채널 API마다 제공하는 필드와 자료형이 다르므로 모든 테이블을 동일한 업무 컬럼으로 맞추지 않는다. 특정 채널에만 배송예정일, 발송지연사유, 정산금액 또는 물류상태 상세코드가 있다면 해당 채널 테이블에만 그 컬럼을 둔다.

API가 제공하지 않는 값을 추론하여 채우거나, 다른 개념의 값을 구매확정·배송완료 등으로 대체하지 않는다. 값이 없으면 컬럼을 만들지 않거나 `NULL`로 저장한다.

### 2.2 주문상품 1건당 1행

한 행은 채널의 논리적인 주문상품 한 건을 나타낸다. 목록·상세·배송 API가 같은 주문상품에 관한 정보를 각각 반환하면 채널 고유 식별자로 결합해 한 행에 적재한다.

동일 주문상품의 응답 내용이 변경되면 기존 행을 수정하지 않고 이력 행을 추가한다. 최신 행만 `IsLatest = 1`로 유지한다.

### 2.3 명시 컬럼과 원본 JSON 병행

주문·배송 업무에서 활용할 가능성이 있는 응답 필드는 SQL 컬럼으로 명시한다. 동시에 마스킹된 원본 응답을 `RawJson`으로 보존해 문서 변경이나 미처 반영하지 못한 필드를 추적할 수 있게 한다.

`RawJson`은 명시 컬럼을 대체하지 않는다. 반복 조회, 필터링, 집계, 조인 대상 필드는 반드시 자료형이 지정된 컬럼에 저장한다.

## 3. 수집 대상 필드 범위

각 채널에서 실제 제공되는 범위 안에서 다음 범주의 필드를 수집한다.

- 주문·주문상품·배송·클레임 식별자
- 판매자 상품, 옵션, SKU 및 외부 연동 식별자
- 상품명, 옵션명, 수량 및 취소수량
- 판매가, 결제금액, 할인금액, 배송비 및 채널별 금액 상세
- 주문, 결제, 발주, 상품준비, 출고, 배송, 배송완료, 구매확정 상태
- 채널 원본 상태 코드, 상태명 및 상태 상세 코드
- 주문일, 결제일, 발주일, 출고예정일, 출고일, 배송완료일, 구매확정일 및 최종변경일
- 택배사, 송장번호, 배송유형 및 물류처리 정보
- 취소·교환·반품·발송지연 관련 상태와 사유
- API가 제공하는 판매채널별 고유 업무 필드

단, 인증키, Secret, Access Token 및 세션 정보는 어떤 형태로도 DB에 저장하지 않는다.

## 4. API 결합 규칙

채널별 수집기는 주문 목록을 페이지네이션으로 완주한 뒤, 필요한 경우 주문 상세 및 배송 상세 API를 추가 호출한다. 여러 API 응답은 다음 순서로 결합한다.

1. 주문 목록에서 수집 대상 주문상품 식별자를 확보한다.
2. 상세 API가 있으면 주문상품별 상세 정보를 조회한다.
3. 배송 API가 분리돼 있으면 주문·주문상품·배송 식별자로 결합한다.
4. 서로 다른 응답에 같은 의미의 필드가 있으면 더 구체적인 상세 API 값을 우선한다.
5. 원본 JSON에는 결합에 사용한 각 API 응답을 출처별 하위 객체로 보존한다.
6. 필수 식별자가 없는 부분 응답은 적재하지 않고 수집 오류로 기록한다.

목록 수집은 API의 최대 조회기간과 페이지 크기를 준수하며, 마지막 페이지까지 수집되지 않은 실행은 성공으로 처리하지 않는다.

## 5. SQL 스키마 변경 방식

기존 테이블은 유지하고 멱등적인 `ALTER TABLE ... ADD` 마이그레이션으로 누락 컬럼을 추가한다. 이미 운영 DB에 존재하는 컬럼의 이름이나 자료형은 데이터 이전 계획 없이 변경하지 않는다.

컬럼 자료형은 다음 기준을 사용한다.

| 응답 유형 | SQL Server 자료형 |
|---|---|
| 외부 식별자·상태 코드 | `nvarchar(100)` 또는 문서상 길이에 맞는 `nvarchar` |
| 상품·옵션·설명 | `nvarchar(500)` 이상 |
| 수량 | `int` 또는 API가 보장하는 정수형 |
| 금액 | `decimal(19,4)`; 원화 정수만 보장하면 `bigint` |
| 일시 | UTC로 변환한 `datetime2(3)` |
| 날짜 | 시간 정보가 없을 때만 `date` |
| 참·거짓 | `bit` |
| 구조화된 반복 객체 | 필요한 항목은 자식 테이블 검토, 그 외 마스킹된 JSON |

배열이 주문상품 한 건에 대해 여러 개 발생하고 독립적으로 조회할 필요가 있으면 자식 테이블을 사용한다. 단일 값을 여러 컬럼이나 구분자 문자열로 압축하지 않는다.

## 6. 개인정보와 원본 응답

이름, 전화번호, 주소, 이메일, 개인통관고유부호 등 개인정보는 현재 수집 모듈의 마스킹 정책을 유지한다. 주문·배송 운영에 반드시 필요한 개인정보를 평문 컬럼으로 추가해야 한다면 저장 목적, 접근권한, 보유기간 및 암호화 방식을 먼저 확정한 뒤 별도 변경으로 처리한다.

이번 확장에서는 개인정보가 아닌 주문·상품·금액·상태·일시·물류 식별 정보 전체를 우선 명시 컬럼화한다.

## 7. 필드 명세 문서

구현과 함께 채널별 필드 사전을 작성한다. 각 행은 다음 정보를 가진다.

| 항목 | 설명 |
|---|---|
| 채널 | 판매채널명 |
| API | 원본 엔드포인트 또는 API 기능명 |
| 응답 경로 | JSON/XML 내 필드 경로 |
| DB 테이블 | 적재 대상 테이블 |
| DB 컬럼 | 적재 대상 컬럼 |
| SQL 자료형 | 실제 컬럼 자료형 |
| NULL 가능 | 값 미제공 가능 여부 |
| 설명 | 채널 문서상 의미 |
| 변환 규칙 | UTC 변환, 코드 보존 등 |
| 검증 상태 | 공식 문서·샘플·실응답 중 확인 근거 |

공식 문서에는 있으나 실응답에서 아직 확인되지 않은 필드는 그 사실을 명시한다. 추측한 필드명은 스키마에 추가하지 않는다.

## 8. 오류 처리

- 목록·상세·배송 API 중 필수 호출 하나라도 실패하면 해당 수집 실행을 부분 성공으로 표시하고 최종 성공으로 커밋하지 않는다.
- 선택적 상세 API 실패 시 어떤 필드가 누락됐는지 실행 로그에 남긴다.
- 응답 자료형이 계약과 다르면 임의 변환하지 않고 원본을 보존한 뒤 오류로 기록한다.
- 알 수 없는 신규 필드는 `RawJson`에 남으므로 데이터가 사라지지 않지만, 필드 사전 검토 후 정형 컬럼 추가 대상으로 등록한다.
- 페이지네이션 중단, 중복 커서 및 빈 중간 페이지를 감지한다.

## 9. 테스트 전략

각 채널은 테스트 우선으로 다음을 검증한다.

1. 공식 문서 또는 비식별 샘플의 모든 선정 필드가 정형 컬럼으로 매핑된다.
2. 목록·상세·배송 응답이 올바른 주문상품 한 행으로 결합된다.
3. 숫자처럼 보이는 외부 ID의 선행 0이 보존된다.
4. 날짜와 시간이 UTC `datetime2(3)`로 변환된다.
5. 상태 코드는 번역하거나 손실하지 않고 원본 그대로 저장된다.
6. 개인정보와 인증정보가 `RawJson`에 평문으로 남지 않는다.
7. 응답 변경 시 새 이력 행이 추가되고 최신 행은 하나만 유지된다.
8. 마이그레이션을 반복 실행해도 오류나 중복 컬럼이 발생하지 않는다.
9. 필드 명세 문서와 실제 SQL·수집기 매핑이 일치한다.

실제 API 호출은 조회 전용 엔드포인트만 사용한다. 발주확인, 발송처리, 취소 또는 상태변경 API는 테스트에서 호출하지 않는다.

## 10. 완료 기준

- 현재 구현된 일곱 개 채널의 주문·배송 API별 필드 목록이 문서화돼 있다.
- 문서에서 수집 대상으로 선정한 모든 비민감 업무 필드가 채널별 SQL 컬럼에 존재한다.
- 수집 모듈이 해당 컬럼을 실제 응답에서 매핑한다.
- 마스킹된 `RawJson`과 정형 컬럼이 함께 적재된다.
- 전체 자동화 테스트와 SQL 계약 검증이 통과한다.
- 각 필드의 출처, 의미, 자료형 및 실응답 검증 여부를 담당자가 확인할 수 있다.

## 11. 범위 제외

- 공통 대시보드 VIEW와 채널 간 상태 표준화
- 지연 판정 및 알림 규칙
- 정산·광고·재고처럼 주문·배송과 별도인 도메인
- 인증·권한이 아직 해결되지 않은 채널의 추측성 테이블
- 외부 상태를 변경하는 API 호출
