# 롯데ON 주문·배송 수집 설계

- 작성일: 2026-09-02
- 시간대: Asia/Seoul (`GMT+09:00`)
- 대상 API: 롯데ON Open API 주문·배송 영역
- 목적: 최근 30일 최초 적재 후 신규 주문과 배송상태를 누락 없이 증분 수집

## 1. 최종 판정

롯데ON 주문·배송 API의 `1일` 제한은 조회 가능한 과거 시점이 아니라 **한 번의 요청에서 지정할 수 있는 검색 시작일시와 종료일시의 최대 간격**이다. 공식 명세의 오류 조건은 `조회기간은 1일을 초과할 수 없습니다`이며, 요청 예제도 하루의 시작과 종료를 사용한다.

따라서 최근 30일 최초 적재는 30일 범위를 한 번에 요청하지 않고 KST 기준 1일 구간으로 나눠 순차 호출한다. 이후 신규 주문은 매일 1일 증분으로 수집할 수 있다.

다만 배송상태 조회의 날짜 검색 기준은 배송상태 변경일시가 아니라 배송지시 생성일시다. 그러므로 매일 직전 1일만 조회하는 방식으로는 과거에 생성된 주문의 배송중·배송완료 등 후속 상태 변경을 놓칠 수 있다. 운영 구조는 다음 두 흐름을 분리해야 한다.

1. 출고/회수지시 생성일 기준 신규 주문 증분 수집
2. DB에 저장된 미완료 주문번호 기준 배송상태 재조회

## 2. 공식 API와 역할

### 2.1 출고/회수지시 주문정보 조회

- Endpoint: `POST /v1/openapi/delivery/v1/SellerDeliveryOrdersSearch`
- 역할: 신규 주문과 클레임의 출고지시·회수지시 수집
- 검색 기준: 출고/회수지시 생성일시
- 기간 조건: 요청 1건의 조회기간은 최대 1일
- 주문번호 조회: 날짜 대신 `odNo`를 사용한 단건 조회 가능
- 주의: 이 API에서 조회된 주문은 이후 상태가 바뀌어도 출고/회수지시 상태로 표현되므로 배송상태 추적에는 사용하지 않는다.

### 2.2 롯데ON 배송상태 조회

- Endpoint: `POST /v1/openapi/delivery/v1/SellerDeliveryProgressStateSearch`
- 역할: 이미 수집한 주문의 현재 배송상태 확인
- 검색 기준: 배송지시 생성일시
- 기간 조건: 요청 1건의 조회기간은 최대 1일
- 주문번호 조회: 날짜 대신 `odNo`를 사용한 단건 조회 가능
- 주의: 공식 명세도 주문수집이 아니라 수집 완료 주문의 실시간 상태 확인 용도로 사용하도록 권장한다.

### 2.3 상태 변경 API 제외

`출고/회수지시 연동완료통보`처럼 롯데ON 주문상태를 변경하는 API는 이번 수집기에서 호출하지 않는다. 모든 운영 호출은 읽기 전용이어야 한다.

## 3. 전체 수집 구조

```text
최초 실행
  └─ 최근 30일을 KST 1일 구간 30개로 생성
      └─ 출고/회수지시 조회
          └─ 정규화·마스킹·중복 판정·DB 적재

매일 실행
  ├─ 신규 주문 수집
  │   └─ 안전 중첩 구간을 KST 날짜별 최대 1일 요청으로 분할
  │       └─ 출고/회수지시 조회 및 적재
  └─ 배송상태 추적
      └─ DB의 미완료 주문번호 조회
          └─ 주문번호별 배송상태 API 호출
              └─ 변경된 상태만 이력 적재
```

신규 주문 수집과 상태 추적은 별도의 실행 단계로 관리한다. 한 단계가 실패해도 다른 단계의 성공 결과는 보존하며, 실패 단계만 재시도할 수 있어야 한다.

## 4. 최근 30일 최초 적재

### 4.1 기간 계산

기준 실행일을 `D`라고 할 때 최초 적재 대상은 `D-30일 00:00:00` 이상 `D 00:00:00` 미만으로 정의한다. 내부 구간은 반개방 구간 `[from, to)`을 사용해 경계 중복과 누락을 방지한다.

API 요청 시에는 롯데ON 형식에 맞춰 다음처럼 변환한다.

```text
내부 구간: 2026-08-01 00:00:00 <= t < 2026-08-02 00:00:00
API 요청: srchStrtDt=20260801000000
          srchEndDt=20260801235959
```

밀리초 단위 원본이 존재할 가능성을 고려해 날짜 경계의 동일 주문이 다음 실행에서 다시 들어와도 DB 멱등성으로 제거한다.

### 4.2 연동완료 주문 포함 검증

`ifCplYN`을 생략하면 공식 명세상 신규 생성 주문이 조회된다. 기존 사방넷이 이미 연동완료 처리한 주문이 최초 적재에서 빠질 수 있으므로 운영키 경계 테스트에서 다음을 확인한다.

1. 같은 과거 1일에 대해 `ifCplYN` 생략, `N`, `Y`를 각각 읽기 전용 호출한다.
2. 각 요청의 반환 건수와 주문 논리키 집합만 기록하고 개인정보·원문 응답은 로그에 남기지 않는다.
3. 연동완료 건을 포함하는 값이 확인되면 백필 설정으로 고정한다.
4. 공식 명세와 실제 응답이 불일치하면 롯데ON API센터 문의 결과를 운영 설정 근거로 기록한다.

### 4.3 보존기간 검증

공식 명세에는 과거 데이터 보존기간이 명시되어 있지 않다. 따라서 30일 적재 가능 여부는 실제 호출로 확정한다.

- `D-1`, `D-7`, `D-14`, `D-30`의 1일 구간을 우선 탐침한다.
- 성공·빈 결과·업무 오류를 구분해 기록한다.
- 빈 결과는 보존 실패로 단정하지 않고 판매자센터 주문 또는 기존 연동 시스템의 집계와 대조한다.
- `D-30`까지 정상 조회된 후 전체 30개 구간을 실행한다.

### 4.4 실행 순서와 재시작

오래된 날짜부터 최신 날짜 순으로 실행한다. 각 일자 구간이 DB에 정상 커밋된 뒤 체크포인트를 완료 처리한다. 중간 실패 시 완료 구간은 건너뛰고 실패 구간부터 다시 실행한다.

## 5. 매일 신규 주문 증분

### 5.1 안전 중첩

매일 전일 달력 날짜만 한 번 조회하지 않고 최소 2시간의 안전 중첩을 둔다. 예를 들어 매일 02:10 KST 실행 시 논리 수집범위는 전일 00:00부터 당일 02:00까지다. API의 최대 1일 조건을 지키기 위해 다음 두 요청으로 분할한다.

```text
요청 1: 전일 00:00:00 ~ 전일 23:59:59
요청 2: 당일 00:00:00 ~ 당일 01:59:59
```

재실행이나 지연 실행 시 마지막 성공 워터마크에서 현재 안전 종료시각까지 날짜별로 다시 분할한다. 중첩으로 발생한 중복은 논리키와 페이로드 해시로 제거한다.

### 5.2 워터마크

신규 주문 워터마크는 마지막 요청 시각이 아니라 **DB 커밋까지 성공한 구간의 종료시각**이다. API 호출 성공 후 DB 저장이 실패한 경우 워터마크를 이동하지 않는다.

### 5.3 지연 데이터 보정

롯데ON 내부 처리 지연에 대비해 최근 3일을 매일 재조회하는 보정 작업을 둔다. 3일은 초기 운영값이며, 첫 4주간 지연 도착 분포를 측정한 뒤 축소하거나 확대한다. 각 날짜는 반드시 별도의 1일 요청으로 호출한다.

## 6. 미완료 주문 배송상태 추적

### 6.1 추적 대상

다음 조건을 만족하는 최신 주문상품을 추적 큐에 포함한다.

- 배송 또는 회수의 종결 상태가 아님
- 마지막 상태 확인시각이 다음 확인 예정시각 이전임
- 영구 실패 또는 운영 제외 상태가 아님

가능하면 주문상품별 호출 대신 같은 `OrderNo`를 가진 행을 묶어 주문번호 한 번으로 조회한다.

### 6.2 재조회 주기

초기 운영 기본값은 다음과 같다.

| 현재 상태 | 재조회 주기 |
|---|---:|
| 출고지시·상품준비중 | 1시간 |
| 배송중 | 3시간 |
| 회수지시·회수중 | 3시간 |
| 배송완료·회수완료·취소 등 종결 | 추적 종료 |
| 알 수 없는 상태 | 6시간, 최대 7일간 추적 후 경고 |

상태 코드의 종결 여부는 설정 테이블 또는 버전 관리되는 매핑으로 유지한다. 알 수 없는 신규 코드는 자동으로 종결 처리하지 않는다.

### 6.3 상태 이력 적재

응답 페이로드의 업무 필드가 직전 최신 행과 같으면 마지막 확인시각만 갱신하고 이력 행은 추가하지 않는다. 상태·송장·택배사·수량·클레임 처리순서 등 추적 필드가 바뀌면 새 이력 행을 삽입하고 이전 행의 `IsLatest`를 해제한다.

## 7. 논리키와 중복 방지

롯데ON 응답은 주문상품 순번 외에 처리순번 `procSeq`를 제공한다. 클레임 발생 시 같은 주문상품의 처리순번이 증가하므로 논리키는 다음과 같이 정의한다.

```text
OrderNo + OrderItemSeq + ProcessSequence
```

여기서 필드 매핑은 `odNo + odSeq + procSeq`다. 기존 `OrderNo + OrderItemSeq`만 사용하면 최초 주문과 교환·반품 등 후속 처리 건이 충돌할 수 있다.

중복 판정은 다음 두 단계로 수행한다.

1. 논리키로 동일 업무 객체 식별
2. 마스킹·정규화한 업무 페이로드의 SHA-256 해시로 동일 상태 재수집 식별

논리키가 같고 해시도 같으면 새 이력 행을 만들지 않는다. 논리키는 같지만 해시가 다르면 상태 변경 이력으로 삽입한다. 최신 행 해제와 신규 행 삽입은 하나의 DB 트랜잭션으로 처리한다.

## 8. 실행 이력과 체크포인트

수집 실행 이력에는 최소 다음 항목을 저장한다.

| 항목 | 설명 |
|---|---|
| `CollectionRunId` | 실행 식별자 |
| `JobType` | `BACKFILL`, `NEW_ORDER`, `STATUS_TRACKING`, `RECONCILIATION` |
| `WindowStart`, `WindowEnd` | KST 논리 조회구간 |
| `RequestCount` | API 요청 수 |
| `ReceivedCount` | 수신 주문상품 수 |
| `InsertedCount` | 신규 이력 행 수 |
| `DuplicateCount` | 동일 해시 중복 수 |
| `ErrorCount` | 실패 요청 수 |
| `Status` | `RUNNING`, `SUCCEEDED`, `PARTIAL`, `FAILED` |
| `StartedAt`, `FinishedAt` | UTC 실행시각 |

체크포인트는 작업 유형별로 분리한다. `NEW_ORDER` 워터마크와 `STATUS_TRACKING`의 주문별 다음 확인시각을 공유하지 않는다.

## 9. 오류 처리와 재시도

- HTTP 429와 일시적 5xx: 지수 백오프와 지터를 적용해 최대 5회 재시도
- 인증 401·권한 403: 즉시 실패 처리하고 운영 알림
- 데이터 형식 오류: 해당 논리키를 격리하고 나머지 건 계속 처리
- 조회기간 초과 오류: 수집기 결함으로 간주하고 자동 일자 분할 후 한 번만 재시도
- DB 저장 실패: API 성공 여부와 무관하게 해당 구간을 미완료로 유지
- 부분 실패: 실행 상태를 `PARTIAL`로 저장하고 실패 구간 또는 주문번호만 재처리

API 키, 인증 헤더, 개인정보, 원문 응답은 로그에 남기지 않는다. 오류 로그에는 채널, 작업 유형, 구간, 주문번호의 비가역 해시, 오류 코드와 재시도 횟수만 기록한다.

## 10. 운영 스케줄

권장 초기 스케줄은 다음과 같다.

| 시각(KST) | 작업 |
|---|---|
| 02:10 | 마지막 성공 워터마크부터 현재 안전 종료시각까지 신규 주문 증분 |
| 매시간 20분 | 출고지시·상품준비중 주문 상태 재조회 |
| 3시간마다 40분 | 배송중·회수중 주문 상태 재조회 |
| 04:30 | 최근 3일 신규 주문 재조회 및 누락 보정 |
| 매주 월요일 05:30 | 최근 30일 일자별 건수·논리키 대사 |

동일 작업의 중복 실행을 막기 위해 채널·작업유형 단위 분산 잠금 또는 DB 애플리케이션 잠금을 사용한다.

## 11. 검증 기준

다음 조건을 모두 만족해야 운영 가능으로 판정한다.

1. 24시간을 초과하는 입력 범위가 KST 1일 이하 요청으로 정확히 분할된다.
2. 월말, 연말, 윤일 경계에서도 구간 누락과 중복이 없다.
3. 30일 백필 중 임의 날짜 실패 후 해당 날짜부터 안전하게 재시작된다.
4. 동일 구간을 두 번 실행해도 동일 페이로드 이력이 중복 삽입되지 않는다.
5. 같은 `odNo + odSeq`에서 다른 `procSeq`가 별도 업무 객체로 저장된다.
6. 과거 주문의 배송상태 변경이 신규 주문 워터마크와 무관하게 수집된다.
7. API 성공 후 DB 실패 시 워터마크가 전진하지 않는다.
8. 종결 상태 주문은 추적 큐에서 빠지고 알 수 없는 상태는 경고와 함께 계속 추적된다.
9. 상태 변경 API가 호출되지 않음을 통합 테스트 또는 호출 허용목록으로 보장한다.
10. 로그와 `RawJson`에 인증정보와 고객 개인정보 원문이 남지 않는다.

## 12. 운영 전 필수 확인

다음 두 항목은 공식 문서만으로 확정할 수 없으므로 운영키를 사용한 읽기 전용 검증이 필요하다.

1. 30일 이전을 포함한 실제 데이터 보존기간
2. `ifCplYN`별 신규·연동완료 주문 포함 범위

이 검증이 끝나기 전에도 수집기 구조는 구현할 수 있지만, 최근 30일 전체 적재 완료를 운영 사실로 선언해서는 안 된다.
