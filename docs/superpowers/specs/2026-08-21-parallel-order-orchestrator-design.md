# 병렬 주문 수집 오케스트레이터 설계

작성일: 2026-08-21
대상 시스템: HMR 채널 주문 수집기
상태: 설계 확정, 구현 전

## 1. 목적

현재 일일 주문 수집 오케스트레이터는 채널을 순차 실행한다. 한 채널이 실패하면 기본 정책에 따라 10분 간격으로 최대 두 번 재시도하며, 이 대기 시간 동안 뒤에 있는 모든 채널의 수집도 중단된다.

본 변경의 목적은 최대 네 개 채널을 동시에 처리하고, 실패 채널의 재시도 대기가 다른 채널의 수집과 적재를 막지 않도록 만드는 것이다. 채널별 데이터 정합성, 중복 실행 방지, 감사 이력 및 기존 종료 코드 계약은 유지한다.

## 2. 범위

### 포함

- 최대 네 개 채널의 병렬 수집 및 적재
- 환경변수를 통한 동시 작업 수 조정
- 실행 시도 단위의 비점유 재시도 예약
- 전체 오케스트레이터 잠금과 채널별 잠금
- 채널별 독립 DB 트랜잭션 및 롤백
- 병렬 실행 결과의 순차적 감사 기록
- 비정상 종료로 남은 오래된 `RUNNING` 감사 행 복구
- 병렬 실행, 잠금, 트랜잭션, 재시도 및 종료 상태 자동화 테스트

### 제외

- Windows 작업 스케줄러 작업을 채널별로 분리
- 채널별 별도 프로세스 실행
- API 수집 로직 또는 채널 테이블 스키마 변경
- 이메일 알림 및 별도 누락 실행 감시기 구현
- 하나의 채널 내부 API 페이지 병렬 호출

## 3. 설정

다음 환경변수를 추가한다.

```env
ORCHESTRATOR_MAX_WORKERS=4
```

- 기본값: `4`
- 허용 범위: `1` 이상, 현재 등록 채널 수 이하
- 현재 등록 채널 수보다 큰 값은 설정 오류로 처리한다.
- `1`을 지정하면 병렬 실행기를 사용하되 실질적으로 순차 실행한다.
- 서버 운영 결과가 안정적이면 `.env` 수정만으로 최대 `8`까지 높일 수 있다.
- Windows 작업 스케줄러 재등록은 필요하지 않다.

기존 설정은 유지한다.

- 기본 재시도 횟수: 최초 시도 이후 2회
- 기본 재시도 간격: 600초
- 명령행의 `--retry-attempts`, `--retry-delay-seconds` 우선 적용

## 4. 실행 구조

### 4.1 중앙 조정기

중앙 오케스트레이터는 다음 역할만 담당한다.

1. 전체 실행 잠금 획득
2. 실행 감사 행 생성
3. 채널별 실행 상태 관리
4. 준비된 시도를 최대 네 개까지 워커 풀에 제출
5. 완료된 결과의 감사 기록
6. 실패 시 다음 재시도 시각 예약
7. 최종 상태 및 종료 코드 집계
8. 전체 실행 잠금 해제

중앙 조정기는 API 응답 데이터나 채널별 DB 트랜잭션을 직접 소유하지 않는다.

### 4.2 시도 단위 워커 풀

고정 크기 `ThreadPoolExecutor`를 사용하며 기본 워커 수는 4개다. 워커 작업 하나는 특정 채널의 특정 시도 한 번만 수행한다.

워커의 처리 순서는 다음과 같다.

1. 채널 전용 DB 연결 생성
2. 채널 잠금 획득
3. 채널 어댑터 생성
4. API 데이터 전체 조회
5. 채널 데이터 DB 적재 트랜잭션 실행
6. 성공 또는 안전하게 분류된 실패 결과 반환
7. 채널 잠금 해제
8. DB 연결 종료

워커 내부에서 재시도 대기나 `sleep`을 수행하지 않는다.

### 4.3 재시도 예약 큐

중앙 조정기는 채널별로 다음 상태를 관리한다.

- 채널명
- 현재 시도 번호
- 다음 실행 가능 시각
- 실행 중 여부
- 최종 결과

실패한 시도에 재시도 횟수가 남아 있으면 다음 실행 가능 시각을 `현재 단조 시간 + 재시도 간격`으로 설정한다. 해당 채널은 지연 우선순위 큐에 들어가며 워커 슬롯과 DB 연결을 점유하지 않는다.

중앙 조정기는 다음 이벤트 중 가장 먼저 발생하는 것을 기다린다.

- 실행 중인 워커 완료
- 지연 큐의 다음 채널 실행 가능 시각 도달

이 구조를 통해 네이버가 10분 재시도를 기다리더라도 쿠팡, 고도몰, 롯데ON 등 다른 채널은 계속 실행된다.

## 5. 잠금 설계

### 5.1 전체 오케스트레이터 잠금

- 리소스명: `HMR_DAILY_ORDER_COLLECTION`
- SQL Server `sp_getapplock` 사용
- 잠금 소유자: 중앙 조정기 전용 DB 세션
- 잠금 범위: 실행 시작부터 모든 채널의 최종 처리 완료까지
- 목적: Windows 예약 실행, 로컬 수동 실행 등 두 개의 전체 오케스트레이터가 동시에 실행되는 것을 방지
- 획득 실패 결과: `ALREADY_RUNNING`, 종료 코드 `2`

중앙 조정기 DB 연결은 워커와 공유하지 않는다. 연결이 종료되면 세션 소유 잠금도 자동 해제된다.

### 5.2 채널별 잠금

- 리소스명: `HMR_ORDER_COLLECTION:{channel}`
- 예: `HMR_ORDER_COLLECTION:naver`
- 잠금 소유자: 해당 시도 워커의 DB 세션
- 잠금 범위: 채널 시도 시작부터 성공 또는 실패 처리 직후까지
- 목적: 전체 오케스트레이터와 수동 단일 채널 적재가 같은 채널을 동시에 변경하는 것을 방지

채널 잠금은 API 조회 전에 획득하고 DB 적재 완료 또는 실패 후 즉시 해제한다. 재시도 대기 중에는 잠금을 유지하지 않으며 재시도 시 다시 획득한다.

채널 잠금을 획득하지 못하면 해당 시도를 잠금 충돌 실패로 기록한다. 다른 채널은 계속 실행하며, 재시도 횟수가 남아 있으면 동일한 재시도 정책을 적용한다.

단일 채널 `--write-db` CLI에도 동일한 채널 잠금을 적용한다. `--dry-run`은 DB를 변경하지 않으므로 채널 잠금을 사용하지 않는다.

## 6. 트랜잭션 경계

채널 하나의 한 번의 시도가 독립적인 업무 단위다.

### API 조회

- 모두 읽기 전용이다.
- DB 트랜잭션을 열기 전에 전체 응답을 조회하고 파싱한다.
- API 조회 실패 시 DB 적재를 시작하지 않는다.
- API 호출은 외부 읽기 작업이므로 DB 롤백 대상이 아니다.

### DB 적재

- API 조회와 파싱이 모두 성공한 뒤 시작한다.
- 해당 채널에서 조회된 레코드 전체를 하나의 DB 트랜잭션으로 처리한다.
- 모든 레코드 저장 성공 시 커밋한다.
- 한 레코드라도 실패하면 해당 채널 시도의 모든 주문 변경을 롤백한다.
- 다른 채널의 트랜잭션과 감사 로그에는 영향을 주지 않는다.

### 감사 로그

- 주문 데이터 트랜잭션과 분리해 독립 커밋한다.
- 실패한 주문 적재가 롤백되어도 시도 시간, 오류 분류 및 0건 결과는 남는다.
- 워커는 결과 객체만 반환하고 중앙 조정기가 완료 이벤트를 받아 감사 로그를 순차 기록한다.
- `AuditRepository` 연결은 한 중앙 스레드에서만 사용해 스레드 간 DB 연결 공유를 금지한다.

## 7. 결과 및 오류 처리

### 채널 성공 상태

- `SUCCESS_WITH_DATA`: API 조회 성공 및 레코드 한 건 이상 처리
- `SUCCESS_EMPTY`: API 조회 성공 및 레코드 0건

### 채널 실패 분류

기존 분류를 유지한다.

- `FAILED_API`
- `FAILED_PARSE`
- `FAILED_DB`
- `FAILED_CONFIG`
- `FAILED_INTERNAL`

채널 잠금 충돌은 운영자가 원인을 구분할 수 있도록 `FAILED_LOCK`을 추가한다.

오류 메시지, 응답 본문, 인증키 및 개인정보는 최종 JSON과 감사 테이블에 저장하지 않는다. 예외 클래스와 안전한 오류 분류만 기록한다.

### 전체 실행 상태

- 모든 채널 성공: `SUCCESS`, 종료 코드 `0`
- 일부 채널 성공: `PARTIAL`, 종료 코드 `1`
- 모든 채널 실패: `FAILED`, 종료 코드 `1`
- 전체 잠금 획득 실패: `ALREADY_RUNNING`, 종료 코드 `2`
- 초기 설정 또는 중앙 DB 연결 실패: `FAILED`, 종료 코드 `2`

결과 배열은 완료 순서와 관계없이 기존 `CHANNEL_NAMES` 순서로 정렬한다. 따라서 병렬 실행 후에도 로그, 감사 결과 및 테스트 출력이 결정적이다.

## 8. 비정상 종료 복구

프로세스 강제 종료, 서버 재부팅 또는 작업 스케줄러 강제 종료 시 `CHANNEL_COLLECTION_RUN.RunStatus='RUNNING'` 행이 남을 수 있다.

새 오케스트레이터는 다음 순서로 복구한다.

1. 전체 SQL 애플리케이션 잠금 획득 시도
2. 잠금 획득에 성공하면 현재 살아 있는 동일 오케스트레이터가 없다고 판단
3. `StartedAt`이 현재 UTC 기준 3시간 이상 지난 `RUNNING` 행을 `ABORTED`로 변경
4. `FinishedAt`에 복구 시각 저장
5. 새로운 `RunId`로 실행 시작

3시간 기준은 현재 Windows 작업 스케줄러의 최대 실행 시간과 맞춘다. 3시간 미만의 과거 `RUNNING` 행은 자동 수정하지 않되, SQL 애플리케이션 잠금을 획득했다면 새로운 실행을 시작할 수 있다. 감사 행의 `RunId`가 다르므로 이력은 구분된다.

오래된 실행 복구 실패는 중앙 감사 DB 오류로 간주하고 신규 실행을 시작하지 않는다.

## 9. 정상 종료와 자원 정리

- 워커 결과와 관계없이 채널 DB 연결을 `finally`에서 종료한다.
- 워커 풀은 모든 제출 작업이 끝난 뒤 종료한다.
- 중앙 감사 행의 최종 상태 저장을 시도한다.
- 중앙 DB 연결 종료로 전체 잠금을 해제한다.
- `KeyboardInterrupt` 등 정상적으로 포착 가능한 중단은 실행을 `ABORTED`로 기록한 뒤 종료한다.
- 프로세스 강제 종료처럼 기록할 수 없는 중단은 다음 실행의 오래된 `RUNNING` 복구 절차에 맡긴다.

## 10. 테스트 전략

### 단위 테스트

- 최대 네 개 시도만 동시에 실행되는지 검증
- 한 채널의 재시도 대기 중 다른 채널이 실행되는지 검증
- 재시도 대기 중 워커 슬롯과 채널 잠금을 점유하지 않는지 검증
- 동일 채널의 두 시도가 동시에 실행되지 않는지 검증
- 결과가 완료 순서와 무관하게 `CHANNEL_NAMES` 순서로 반환되는지 검증
- 최대 재시도 횟수와 시도 번호가 기존 계약과 같은지 검증
- 워커 예외가 다른 채널 작업을 중단하지 않는지 검증
- `ORCHESTRATOR_MAX_WORKERS`의 기본값과 1~8 검증

실제 10분을 기다리지 않도록 단조 시계, 대기 함수 및 실행기를 주입 가능한 구조로 만든다.

### 잠금 및 트랜잭션 테스트

- 전체 잠금 실패 시 아무 채널도 실행하지 않는지 검증
- 채널 잠금 획득·해제가 시도마다 한 번씩 수행되는지 검증
- 채널 실패 후 재시도 대기 전에 잠금이 해제되는지 검증
- 채널 적재 중 한 레코드 실패 시 해당 채널 전체가 롤백되는지 검증
- 다른 채널의 성공 트랜잭션은 유지되는지 검증
- 감사 로그가 주문 롤백과 별도로 남는지 검증

### 통합 검증

- 합성 어댑터 8개로 최대 동시 실행 수 확인
- 한 채널을 의도적으로 실패시키고 나머지 채널 완료 확인
- SQL Server에서 전체 잠금과 채널 잠금 충돌 동작 확인
- 오래된 `RUNNING` 행의 `ABORTED` 전환 확인
- 기존 Windows 실행 스크립트가 수정 없이 새 오케스트레이터를 호출하는지 확인
- 전체 회귀 테스트 통과 확인

## 11. 운영 적용 및 롤백

1. 로컬 합성 테스트 및 전체 회귀 테스트 실행
2. 로컬 SQL Server 대상 잠금·감사 통합 검증
3. `ORCHESTRATOR_MAX_WORKERS=4`를 서버 `.env`에 추가
4. 서버에서 스케줄러와 같은 명령으로 수동 1회 실행
5. 감사 테이블의 채널별 시작·종료 시각이 겹치는지 확인
6. 채널별 적재 건수와 최종 종료 코드 확인
7. 다음 14:00 예약 실행 확인

문제가 발생하면 `ORCHESTRATOR_MAX_WORKERS=1`로 변경해 코드 배포 상태를 유지하면서 순차 실행으로 즉시 되돌릴 수 있다. 스케줄러 재등록이나 데이터 테이블 롤백은 필요하지 않다.

## 12. 완료 기준

- 최대 네 채널이 동시에 실행된다.
- 실패 채널의 재시도 대기가 다른 준비 채널의 실행을 막지 않는다.
- 같은 채널은 동시에 두 번 적재되지 않는다.
- 채널별 적재는 독립적으로 커밋 또는 전체 롤백된다.
- 실패 채널이 있어도 나머지 채널은 끝까지 실행된다.
- 감사 테이블에 모든 시도와 최종 실행 상태가 정확히 남는다.
- 기존 종료 코드와 개인정보 비노출 계약을 유지한다.
- `ORCHESTRATOR_MAX_WORKERS=1`로 순차 실행 호환이 가능하다.
