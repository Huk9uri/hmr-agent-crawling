# HMR 판매채널 주문 수집 자동화 인수인계서

## 1. 프로젝트 개요

- **목적:** 판매채널별 주문·주문상품·배송·클레임 정보를 공식 API로 정기 수집하여 SQL Server에 이력 형태로 적재하고, 후속 현황 집계와 이상 주문 분석의 원천 데이터를 제공한다.
- **요청 부서·주요 사용자:** 전략영업팀 SCM 업무 담당자, 주문 현황 데이터 분석·운영 담당자
- **시작일:** 2026-08-07
- **완료 기준:** 운영 서버에서 매일 14:00 KST 자동 수집이 정상 실행되고, 채널별 주문 이력과 실행·시도 감사 이력을 SQL Server에서 확인할 수 있으며, 장애 시 수동 재실행·백필·복구 절차가 문서화된 상태
- **현재 한 줄 요약:** 기존 8개 채널의 운영 배포와 스케줄러 활성화를 완료했으며, 카카오쇼핑은 API 키 발급 후 즉시 검증·활성화할 수 있도록 구현까지 완료한 상태다.

## 2. 현재 상태

- **현재 단계:** 운영 및 신규 채널 연동 준비
- **최근 완료 항목:** 네이버·롯데ON 최초 30일 백필, 일일 증분 수집 운영 배포, 동시 실행 수 4개 적용, 카카오쇼핑 어댑터·DB·감사 이력·가변 기간 백필 구현 및 `main` 병합
- **진행 중인 항목:** 카카오쇼핑 연동 권한과 API 키 발급 대기
- **다음 액션:** 카카오 키 발급 → 운영 `.env` 등록 → 짧은 기간 `--dry-run` → DB 생성·검증 SQL 적용 → 수동 실행과 이력 확인 → `KAKAO_SHOPPING_ENABLED=true` 전환
- **막힌 점·의사결정 필요사항:** 카카오쇼핑 선물하기 API 권한 부여 여부, 실제 과거 주문 제공 범위, 기업 SMTP 계정 및 누락 실행 감시·알림 도입 여부

## 3. 업무 범위와 운영 흐름

1. **업무가 시작되는 조건:** Windows 작업 스케줄러의 `HMR Daily Order Collection` 작업이 매일 14:00 KST에 시작한다. 수동 백필 또는 장애 복구 시에는 운영자가 명령을 직접 실행한다.
2. **처리 순서:** 환경설정 로드 → 실행 중복 방지 잠금 → 활성 채널을 최대 4개씩 병렬 실행 → 채널 API 목록·상세 조회 → 개인정보 마스킹 및 중복 제거 → 채널별 이력 테이블 적재 → 실행·시도 결과 기록 → 로그 출력
3. **결과 확인 방법:** 작업 스케줄러의 마지막 실행 결과가 `0x0`인지 확인하고, 로그 파일과 `CHANNEL_COLLECTION_RUN`, `CHANNEL_COLLECTION_ATTEMPT`의 상태·건수를 함께 확인한다.
4. **정기적으로 해야 하는 일:** 일일 성공 여부와 채널별 실패 확인, API 인증키 만료·IP 허용 상태 점검, 로그 용량 확인, 신규 필드·정책 변경 공지 확인
5. **예외 상황 대응:** 실패 채널만 원인을 확인한 뒤 수동 재실행한다. 기간 누락은 채널 정책에 맞는 백필 명령으로 보정한다. 중복 실행은 애플리케이션 잠금으로 차단되며, 3시간 이상 남은 `RUNNING` 감사 행은 다음 실행에서 `ABORTED`로 복구된다.

## 4. 시스템·작업 환경

- **사용 도구·서비스:** Python 3.12, PowerShell, Windows 작업 스케줄러, SQL Server, 각 판매채널 공식 Open API, Git
- **저장소·폴더 위치:** 개발 저장소 `C:\workspace\HMR_Agent_Crawling`, 운영 서버 `C:\Users\Administrator\Desktop\iyeon_RPA\HMR_Agent_Crawling`
- **운영 화면·대시보드:** Windows 작업 스케줄러의 `\iyeon_RPA\ecommerce\HMR Daily Order Collection`, SQL Server 감사 테이블, 각 판매채널 API·판매자센터
- **배포·실행 방법:** 검증된 전체 프로젝트 ZIP을 운영 서버에 복사·교체한 뒤 `.env`와 `.venv`를 유지하고 스케줄러를 재활성화한다. 수동 실행은 `python -m hmr_order_collection.orchestrator --config .env` 형식을 사용한다.
- **로그 확인 위치:** `C:\ProgramData\HMR_Order_Collection\logs`
- **권한 요청 담당자·절차:** 채널별 판매자센터 관리자 또는 담당 MD에게 API 권한·인증키·운영 서버 공인 IP 등록을 요청한다. DB와 서버 접근 권한은 사내 시스템 관리자 절차를 따른다. 비밀값은 Git에 저장하지 않고 승인된 운영 서버 `.env`에서만 관리한다.

> 🔐 비밀번호, API 키, 개인정보는 이 문서에 기록하지 않는다. 회사에서 승인한 운영 서버 `.env` 및 접근 통제된 보관 위치와 권한 요청 절차만 공유한다.

## 5. 주요 기능·구조

- **핵심 기능:** 채널별 주문 수집, 날짜 구간 분할, 페이지네이션, 상세조회, 중복 제거, 변경 이력 적재, 개인정보 마스킹, 병렬 실행, 재시도, 실행 감사
- **데이터 입력:** 네이버, 쿠팡, 고도몰, 롯데ON, 11번가, SSG.COM, CJ온스타일, 토스쇼핑의 공식 API 응답. 카카오쇼핑은 활성화 전 대기 상태다.
- **처리 로직:** 채널 고유 주문·주문상품 키와 payload hash를 비교하여 동일 데이터는 건너뛰고, 변경된 경우 기존 최신 행의 `IsLatest`를 해제한 후 새 이력 행을 추가한다.
- **결과물·출력:** 채널별 `*_ORDER_ITEM` 테이블, `CHANNEL_COLLECTION_RUN`, `CHANNEL_COLLECTION_ATTEMPT`, 건수 중심 운영 로그
- **외부 연동:** 판매채널 공식 API, SQL Server, Windows 작업 스케줄러
- **주의할 의존성:** 운영 서버 공인 IP 허용, API 인증키 유효성, 서버 `.env`, Python 가상환경, SQL 테이블·인덱스 선적용, 시스템 계정의 폴더·로그 쓰기 권한

## 6. 알려진 오류와 주의사항

| 구분 | 증상 | 발생 조건 | 임시 대응 | 근본 해결 여부 |
|---|---|---|---|---|
| 시간대 | `CollectedAt`이 예상보다 9시간 이전으로 보임 | UTC 저장값을 KST로 해석 | 조회·보고 시 UTC→KST 변환 | 설계상 정상 |
| 스케줄러 | 작업 이름을 찾을 수 없음 | `TaskPath`를 빼거나 잘못 지정 | `TaskPath='\iyeon_RPA\ecommerce\'`와 정확한 이름 사용 | 운영 절차 반영 |
| 배포 | ZIP 압축 해제 시 동일 파일 오류 | 기존 폴더 위에 바로 해제 | 스케줄러 중지 후 별도 폴더에 해제하고 검증 후 교체 | 운영 절차 반영 |
| 배포 | 운영 폴더 이름 변경 실패 | 메모장·Python·작업 스케줄러가 파일 사용 중 | 관련 프로세스 종료 후 교체 | 운영 절차 반영 |
| API | 채널 한 곳만 실패 | 키 만료, 등록 IP, 일시적 429·5xx, 정책 변경 | 감사 이력의 `ErrorCategory`와 로그 확인 후 해당 채널 재실행 | 채널별 확인 필요 |
| 데이터 | 일일 요청 구간 경계에 주문이 중복됨 | 네이버의 의도적 경계 중첩 | 주문상품 고유 ID로 중복 제거 | 구현 완료 |
| 카카오 | 활성화 시 설정 오류 | 키 또는 채널 ID 누락 | `KAKAO_SHOPPING_ENABLED=false`로 기존 채널 운영 유지 | 키 발급 후 검증 필요 |
| 모니터링 | 작업 누락을 즉시 알리지 못함 | SMTP·별도 감시 작업 미구축 | 매일 스케줄러와 감사 테이블 수동 확인 | 미해결 |
